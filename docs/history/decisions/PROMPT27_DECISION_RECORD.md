# Prompt 27 Engineering Decision Record

## Production composition

The existing `--demo foundation` CLI route now owns
`visual_foundation.Scene`. That scene directly composes the Prompt 26
environment presentation and its Prompt 25 male/female character instances.
The earlier procedural `foundation_playground.Scene` remains a focused Prompt
22 regression module and collider-data authority; it is not a competing
rendered application.

## Interaction presentation

The previous handshake side-view request and contact-order overrides were
manager constants. They are now a validated
`interaction.PresentationDefinition`: two role views, a suppression flag, and
a typed occlusion-profile ID. This is the smallest data model that makes
interaction view and ordering declarative without callbacks or speculative
capacity growth. The existing four manager-owned override slots remain
sufficient.

Wardrobe order previously always used neutral interaction layer zero. It now
inherits only the interaction layer from the actual bound anatomy semantic
while preserving the garment's own body-part layer. Gloves and other bound
equipment therefore participate without item IDs or outfit-specific
handshake branches.

## Side interaction projection

The first real D3D12 contact capture proved that authoritative post-IK sockets
could coincide while the side-art arms rendered downward. Ordinary side
projection remapped both arm rests for idle profile readability, discarding
the visual plane of the authored handshake. Interaction-owned side projection
now preserves the participating right-arm animation/IK plane, retains profile
treatment for the other arm and legs, and leaves authoritative
pose/socket/root state untouched.

## Front-facing proof

A second visible interaction would require additional authored clips without
strengthening the current production handshake. Prompt 27 uses the allowed
deterministic definition proof: a validated synthetic presentation selects
front/front with no occlusion profile. No fake greeting mechanics or root
constraints were added.

## Properties and wardrobe

Movement speed, jump strength, double jump, and dash are base character
properties in the production wardrobe definition. Wardrobe items remain
cosmetic: every item still has zero modifiers and zero capability grants.
Changing appearance cannot change interaction sockets or eligibility.

## Bounds

All eight atlas pages and two garment mesh definitions load at initialization.
The 2,100-frame route performs no steady-state image decode, filesystem read,
GPU resource creation, simulation allocation, submission allocation, or queue
allocation. Interaction records, presentation claims, override handles,
outfit IDs, theme IDs, debug state, and capture scheduling are fixed-capacity.

Interactive shutdown validates the common decoded-page, sprite-submission,
allocation, and GPU-resource bounds, but does not claim completion of the
scripted matrix. Mesh-use, nine-capture, and milestone completeness remain
scripted-only acceptance requirements. This keeps a user-requested interactive
exit honest without weakening the deterministic route.
