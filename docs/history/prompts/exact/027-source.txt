# Prompt 27 — Integrated Visual Foundation, View-Aware Interaction Presentation, and Final Art/Gameplay Acceptance

## Engineering brief

### Purpose

Prompts 23–26 establish:

- real art assets;
- side/front character views;
- actual male/female visual identity;
- a large modular wardrobe;
- environment art;
- environment themes;
- clear collision readability.

Prompt 27 proves that these systems work together as a game rather than as isolated rendering demos.

This should become the new:

"show me what this game could become"

playground.

The milestone must give a useful first answer to two questions:

### What can the game look like?

We should be able to see:

- a coherent male character;
- a coherent female character;
- front idle;
- side locomotion;
- multiple real outfits;
- breathing;
- hair/cape motion;
- atmospheric world art;
- clear platforms;
- layered parallax.

### How do character interactions look/work?

The existing handshake must now be presented through the real art system.

Prompt 27 should also make interaction presentation a first-class concept:

interaction

→ role animation

→ required character view

→ IK/contact correction

→ participant/body-part occlusion

→ cleanup

This is the foundation for later:

- hugs;
- carrying;
- sitting;
- furniture interactions;
- front-facing cinematic interactions;
- other paired poses.

Do not implement all of those now.

The architecture must not make them impossible.

### Critical scalability principle

Simulation and presentation remain separated.

A future interaction may choose:

- side;
- front;
- back;
- 3/4;
- a special authored view.

The existing interaction manager should not become hardcoded to:

handshake == side forever

Instead, presentation requirements should be declarative interaction data where appropriate.

Build the integrated visual-foundation acceptance route and strengthen the existing interaction presentation boundary so real character art, view selection, clothing, occlusion, IK, environments, and gameplay all operate correctly together.

## 8. Future interaction architecture documentation

Without implementing the mechanics, document how the current architecture could expand to future interaction classes.

### Multiple body contacts

Future paired animation may define multiple semantic targets:

- hand-to-hand;
- hand-to-shoulder;
- hand-to-torso;
- etc.

Authored animation should remain primary.

IK should provide corrective alignment rather than inventing entire complex poses.

### Root-relative interactions

Future carrying/lifting poses may require a bounded participant-relative root constraint.

Do not implement it now.

Document why the current fixed-root handshake does not provide that behavior.

### Prop/world-anchor interactions

Future:

- chairs;
- beds;
- ledges;
- doors;

may expose semantic interaction anchors.

Do not implement that system now.

Document the likely boundary.

### View-specific/cinematic interactions

Future interactions may request:

- front;
- back;
- 3/4;
- custom authored viewpoint.

The view system implemented in Prompt 24 must remain capable of supporting this.

Do not implement those production assets now.
